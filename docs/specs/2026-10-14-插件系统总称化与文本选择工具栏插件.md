# 规格说明书：插件系统总称化 + 文本选择工具栏插件

日期：2026-10-14
状态：已对齐（grill-with-docs 共识，见 CONTEXT.md 与 docs/adr/0002）

## 1. 问题陈述

当前插件系统只有一种类型：文本处理插件（整条剪贴板文本进、新文本出，Worker 沙箱执行，单启用）。这限制了插件的想象空间——很多有用的插件并不产生新文本，而是针对**选中的文本区段**做动作：跳转到选中的网址、把选中的代码片段复制到剪贴板、把 ISBN 送往豆瓣搜索等。

同时，「插件」这个词在代码、UI、文档中都与文本处理插件绑死，没有为未来更多插件类型留出结构位置。

本次变更：把「插件系统」重构为按类型划分的子模块总称，并新增第二种插件类型——**文本选择工具栏插件**。

## 2. 方案概述

- 引入插件类型（`type`）概念：`text-transform`（现有，行为不变）与 `selection-toolbar`（新增）。.CVT 元数据新增 `type` 字段，缺省视为 `text-transform`，存量文件零改动兼容。
- 文本选择工具栏插件复用现有选区工具栏（`SelectionToolbar.tsx`）作为宿主：选中 `.content-text` 内文本后，宿主用各插件元数据中的**声明式正则**匹配选区文本，命中的插件按钮出现在工具栏上。
- 该类型插件**免沙箱**，在主线程以 `new Function` 执行，可用全部 Web API（详见 ADR 0002）。
- 单一文本入口、无出口：插件返回值不产生新文本，仅表达成功/失败。
- 工具栏插件**多启用并存**；文本处理插件维持单启用不变。
- 服务端 `plugins` 表加 `type` 列，复用现有 CRUD 路由；启用语义按类型区分。

## 3. 用户故事

### 解析与导入

1. 导入一个元数据含 `"type": "selection-toolbar"` 的 .CVT，若同时含合法 `regex` 与 `button_name`（1–8 个字符），解析成功，插件以工具栏类型入库。
2. 导入 `type: "selection-toolbar"` 但 `regex` 缺失、或 `new RegExp(regex)` 抛错的 .CVT，导入失败并提示具体原因。
3. 导入 `type: "selection-toolbar"` 但 `button_name` 缺失或超 8 个字符的 .CVT，导入失败并提示。
4. 导入无 `type` 字段的 .CVT（存量格式），按文本处理插件解析成功，行为与现状完全一致。
5. 导入 `type` 为未知值的 .CVT，导入失败并提示。

### 插件管理 UI

6. 插件管理页按类型分区展示：文本处理插件区、文本选择工具栏插件区，各自独立列表与操作。
7. 工具栏插件可多个同时启用，互不影响；启用一个工具栏插件不清空其他工具栏插件的启用状态。
8. 启用/禁用文本处理插件时，工具栏插件的启用状态不受影响，反之亦然。
9. 同一 id 重复导入按现有逻辑视为更新（含类型字段的更新）。

### 工具栏行为（仅桌面模式）

10. 选中条目正文（`.content-text`）文本后，宿主将选区文本与所有已启用工具栏插件的正则做匹配（`RegExp.test` 语义），命中的插件以「按钮名」显示在工具栏上，与现有「复制文本」「跳转到网页」按钮并列。
11. 多个插件正则同时命中时，全部按钮并列显示，互不干扰。
12. 无任何插件命中时，工具栏只显示现有内置按钮，行为不变。
13. 插件按钮被点击后，工具栏收起，插件代码开始执行，入口参数为选区文本（字符串）。
14. 插件代码执行 resolve：弹出站内成功通知（toast）；`resolve(自定义文案)` 时 toast 显示该文案，无参 resolve 显示默认文案（含插件名）。
15. 插件代码执行 reject 或抛出异常：弹出站内失败通知；reject 值为 `Error` 时显示其 message，否则显示通用失败文案（含插件名）。
16. 插件执行发生在主线程、可访问全部 Web API：例如插件内可 `window.open(url)` 跳转、`navigator.clipboard.writeText(text)` 复制，无需宿主提供额外动作 API。
17. 工具栏插件的安装、导入交互与现有插件一致（手动导入 .CVT）。

### 服务端

18. `POST /api/plugins` 与 `PATCH /api/plugins/:id` 接受并持久化 `type`；`GET` 返回 `type` 字段。
19. 单启用约束（enable 时清零他人 enabled）仅作用于 `type = 'text-transform'` 的插件。

## 4. 已定决策

| 决策 | 内容 | 出处 |
|---|---|---|
| 正则归属 | 声明式，写在 .CVT 元数据，宿主执行匹配；插件代码不参与匹配 | 拷问 Q1 |
| 执行模型 | 免沙箱，主线程执行，完全开放 Web API，宿主仅提供通知 | ADR 0002 |
| 启用模式 | 工具栏插件多启用并存；文本处理插件维持单启用 | 拷问 Q3 |
| 反馈约定 | 插件体支持 async，resolve=成功 / throw=失败，宿主自动 toast，resolve 可带自定义文案 | 拷问 Q4 |
| 通知形式 | 站内 toast（复用现有 notice-toast），不用系统通知 | 拷问 Q5 |
| 平台范围 | 仅桌面模式；移动端选区工具栏维持禁用 | 拷问 Q6 |
| 存量兼容 | 文本处理插件的沙箱、单启用、UI 全部保持现状 | 拷问 Q7 |

## 5. 测试决策

接缝选择（优先复用已有接缝）：

- **`parseCvt()`**（`web/src/plugins/parseCvt.ts`）— 类型字段与工具栏元数据校验全部在这里，纯函数，是本变更最高的测试靶心。故事 1–5 全部可在该接缝验证。
- **服务端 validation schema + 路由**（`server/src/validation.ts`、`server/src/routes/plugins.ts`）— type 持久化与按类型启用语义。故事 6–9、18–19 在此验证（现有插件路由的测试方式沿用）。
- **选区→插件匹配**抽出为纯函数（输入：选区文本 + 已启用工具栏插件列表；输出：命中的插件列表），故事 10–12 在此验证，UI 组件本身不作为主要测试靶。
- 故事 13–17（执行、toast、工具栏收起）为手工 UI 验收：浏览器中导入一个「跳转豆瓣搜索」示例插件验证全流程。用户按惯例负责手工测试，提供精确步骤与预期日志。

「完成」的定义：parseCvt 与匹配纯函数的自动化测试全绿；服务端启用语义测试通过；示例插件在浏览器中完成选中→按钮出现→点击→toast 反馈全链路。

## 6. 明确不做

- 移动端选区工具栏及工具栏插件支持。
- 文本处理插件的任何改动（沙箱、单启用、`PluginConfirmModal` 流程）。
- 插件市场、在线分发、签名或信任机制。
- 服务端执行插件代码的任何路径（插件仅运行于客户端浏览器）。
- 宿主提供的 openUrl/copy 等动作 API 封装（插件直接用 Web API）。
- 第三种及更多插件类型（总称架构仅为它们预留位置，不预实现）。

## 7. 补充说明

- **CVT 格式演进**：`CvtMeta` 新增 `type?: 'text-transform' | 'selection-toolbar'`；工具栏插件额外要求 `regex: string`（导入时用 `new RegExp` 校验合法性）与 `button_name: string`（1–8 字符）。正则匹配语义为 `RegExp.test`（子串匹配，非全匹配）。
- **执行约定**：工具栏插件代码体沿用 `process(input)` 函数名以复用解析逻辑；宿主以选区文本为 `input` 调用，`await` 其返回值，resolve/reject 决定 toast。
- **通知复用**：站内 toast 复用 App 现有 `notice` 机制；`SelectionToolbar` 需要从 App 获取触发通知的回调（prop 传入），不另起通知系统。
- **工具栏宽度**：现有工具栏宽度按有无 URL 按钮硬编码计算，插件按钮加入后定位逻辑需按实际按钮数量自适应。
- 相关文档：`docs/PLUGINS.md` 需同步补充新类型的 .CVT 编写说明；`CONTEXT.md` 已收录术语。
